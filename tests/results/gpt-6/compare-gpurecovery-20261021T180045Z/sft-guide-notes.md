# New CUDA SFT evidence

Sixteen new native SFT cases completed on one NVIDIA GeForce RTX 5060 (8 GiB, compute capability 12.0): TRL, LLaMAFactory, ms-swift and Axolotl each ran a seeded tiny Qwen2 model with full training and Qwen3-0.6B with LoRA, in requested FP32 and BF16 modes. Every case completed the original framework training workflow, one native SGD update, a separate CPU execution, and five skill comparisons. These are single-GPU results. Four-GPU DDP and official CUDA Megatron Bridge completion are separate outstanding execution scopes.

The native entrypoints were `trl.SFTTrainer.train`, `llamafactory.train.tuner.run_exp`, `swift.pipelines.train.sft.sft_main` and `axolotl.cli.train.do_cli`. The latter three include their original data preprocessing, model/trainer preparation and workflow completion/save paths. Passive callbacks observed the original loss return, forward logits, synchronized gradients before optimizer mutation, initial stored parameters and stored parameters after the optimizer. No numerical operator or framework optimizer was replaced. SGD used learning rate 0.001, zero momentum/weight decay/clipping, accumulation 1, and one step. Pretrained LoRA used q/v projections, rank 4, alpha 8 and zero dropout; full adapter gradients, present-zero A coordinates, stored updates and frozen-base unchanged hashes were retained.

The CPU process reads only a dedicated input package containing initial trainable values, prepared inputs, model/loss controls and initial storage/frozen-state information. It independently reloads the original checkpoint and recomputes eager FP32 forward, objective, backward and SGD. It never deserializes native gradients or post-update values for execution. Native frozen BF16/F16 values, when present, are reproduced before FP32 computation and checked by numeric-value hashes. CPU parameter devices/dtypes and its world size of one are recorded explicitly. The native and reference topology must not be described as distributed equivalence merely because their software installation is shared.

Each native/reference pair uses exactly the same captured ordered token IDs, labels, masks and active EOS. The original frameworks resolve their own templates and preprocessing, so examples and valid-target counts can differ between frameworks; the retained comparisons are each framework against its independently recomputed CPU reference. They do not establish an aligned comparison between frameworks. For future four-GPU TRL runs, all four native dataset examples have identical content; `audit_ddp.py` checks actual per-rank completion, equal initial state and ordered batches, and equality of synchronized gradient replicas. It reports the observed native-to-CPU gradient scaling without calling the single-process CPU reference a four-rank run.

Native objective values retain their implemented denominator. They are not necessarily the mean NLL over the selected shifted targets. For example, the retained TRL pretrained path passes `num_items_in_batch=18` while exposing 17 valid shifted targets. The CPU reference replays that denominator, while the target-score comparator separately reports the 17-target NLL. Each public summary includes the captured native controls and valid shifted-target count. Original native tensor dtypes remain unchanged in PT and safetensors; distribution logprobs are derived offline using full-vocabulary FP64 log-softmax. Requested BF16 does not imply every native parameter or gradient is BF16, and separate master storage is not inferred from exported FP32 copies.

TRL used the existing read-only environment: PyTorch 2.8.0+cu128, Transformers 4.57.1 and TRL 0.24.0. Its post-run full-environment `pip check` exits 1 because the existing environment contains incomplete or conflicting metadata for unexecuted older Axolotl/Swift/Factory installations and other packages; that receipt is retained. The successful TRL workflow is not presented as a clean installation of every framework named in that old environment. LLaMAFactory 0.9.5 used a new isolated PyTorch 2.9.0+cu128 environment with Transformers 5.3.0, TRL 0.24.0, Accelerate 1.11.0, PEFT 0.18.1 and datasets 4.0.0. ms-swift 4.6.0 used a separate isolated PyTorch 2.9.0+cu128 environment with Transformers 5.3.0, TRL 0.29.1, Accelerate 1.14.0, PEFT 0.20.0 and datasets 4.8.4. Axolotl 0.17.0 used an isolated PyTorch 2.10.0+cu128 environment with its supported pinned Transformers 5.9.0, TRL 1.5.1 and xformers 0.0.34. All three new native environments pass a fresh post-run `pip check`. The summaries retain actual versions for every case, rather than presenting one version set for the whole matrix.

Two dependency failures were preserved and resolved before counting native completion. First, PyArrow 26.0.0 resolved against NumPy 1.26.4 but failed at import because that runtime requires NumPy 2.0 or newer. NumPy 1.26.4 profiles now explicitly pin PyArrow 21.0.0. Second, Swift 4.6.0 declares a datasets range admitting 4.0.0 but imports `datasets.features.Json`, which that version lacks. A shared Factory/Swift environment therefore passed dependency resolution and `pip check` while failing Swift preprocessing. The successful Swift run uses its separate datasets 4.8.4 environment; Factory retains its own supported datasets 4.0.0 environment. Resolver success and `pip check` alone are not recorded as native execution or runtime-semantic compatibility. Axolotl also logs that optional torchao C++ extensions require a newer Torch version; the selected unquantized, eager-attention, non-Liger training path completed using its actual native operators, with that warning retained.

Qwen3-0.6B was requested at fixed Hugging Face revision `c1899de289a04d12100db370d81485cdf75e47ca`, and every checkpoint file's SHA256 and size were captured. Original case identity records retain `local_source_revision_verified=false`: collection itself did not authenticate the local snapshot against Hub metadata. The parent's independent post-hoc `SOURCE_IDENTITY_AUDIT.json` checks the saved identities against that revision without changing historical case bytes.

Public v2 exports use the skill evidence tool's explicit literal replacements for the hostname and private work/environment roots. All archives are below 90 MiB, retain byte-identical protected numerical files, pass indexed verification, and independently replay all five comparisons. Public audit receipts scan the hostname across every retained byte and private roots across retained text. The summaries contain all numeric reports and preserve the native-objective/target-NLL distinction. Replay verifies retained evidence and recomputes its metrics; it does not repeat native training. All comparison thresholds are null and no numerical precision acceptance is claimed.

Official CUDA Bridge preparation is tracked independently. The selected upstream source is NVIDIA Megatron Bridge v0.2.0, commit `7af9601c9da746d21481194356295bfe23df3737` (annotated tag object `717c62de401bce92e913fd1c66c03f4e17bff265`), with Megatron Core 0.15.0, authentic Transformer Engine 2.9.0 and Transformers 4.57.1. The source adapter performs real HF conversion, native checkpoint save/restore and `finetune`; its pretrained gradient/update evidence explicitly samples the first 4096 elements of every logical tensor while retaining the complete logical inventory. Dependency resolution and CUDA extension builds are preparation only and do not count as Bridge native completion. The TE extension progressed through a real CUDA build after adding authentic NVIDIA header directories. A subsequent source build exhausted the small WSL RAM/swap allocation; only the Bridge build processes were stopped, WSL remained running and its available memory recovered above 14 GiB. Further Bridge builds move to the remote large-memory environment. No NPU fork result is relabeled as CUDA completion.
