# Execution workflow

## Prepare and run

Reuse agreed scope, configurations, artifacts and approvals. Resolve facts from records/code; choose routine paths, formats, hooks and timeouts yourself. Ask only for an unresolved decision that changes task semantics or authorization.

Before device execution, establish command, allocation, output location, remaining cumulative budget and timeout. Include loading, failed attempts, collection and cleanup. Use the existing environment manager/scheduler; verify allocated-device mapping and idleness. Resolve skill-owned launch, capture and comparison failures within scope/budget. Record native-library import/API/execution blockers without editing library source or inventing compatibility methods; select a supported per-platform combination within the user's approved comparison scope. Resolve changes to experimental semantics or scope before proceeding.

When process shutdown is asynchronous, reserve time for bounded device-idleness rechecks and keep execution failure separate from cleanup completion.

Save replayable inputs/state, observations, effective settings, run-associated environment and every rank's completion evidence. Validate each side before pairing; reuse valid evidence rather than rerunning for a preferred filename or layout.

## Report and hand off

Report numerical differences and continue collection whose inputs, semantics and coverage remain valid. Missing or incompatible evidence blocks its affected comparison. When localization is in scope, start at a discrepant position, tensor or stage and collect evidence that distinguishes likely causes. Library repair and precision remediation are outside this skill.

When reviewing whether a difference comes from execution or the native stack, separate collector inputs/calls/mapping errors from reproducible library behavior under the agreed configuration. Use existing source and artifacts, then the smallest discriminating validation. Correct collection/provenance mistakes with a regression; retain native library findings without changing operators or versions to reduce the difference. A same-input cross-backend replay is useful when needed, but a different-input historical result is not an oracle.

A handoff contains shared conditions, observations, environment/launch evidence, validator and a short next step. Preserve failed attempts and historical runs; create new runs exclusively. Either side may execute first.

Report outcome, principal metrics, coverage, blockers and evidence link. Distinguish software tests, device execution and numerical agreement; keep detailed inventories and tables in artifacts.
