# 架构设计

[返回 README](../README.md) · [工作流与校验规则](WORKFLOW.md)

## 1. 三层职责

| 层 | 职责 | 交接边界 |
|---|---|---|
| 通用 agent 协议 | 组织比较条件与授权，按需拆分任务，调查并转交缺口 | 按 [原子任务](WORKFLOW.md#11-有界原子任务)交接和验收 |
| 确定性校验核心 | 核验身份、语义、状态、坐标及覆盖，负责比较算法与判定 | 接收冻结契约与双侧产物，独立离线计算；接口与支持范围见 [最小比较器](WORKFLOW.md#22-最小比较器) |
| 库执行器 | 保留原生接口，准备输入状态，采集并交付运行事实与观测 | 按 [采集验收](WORKFLOW.md#12-采集先行与交付验收)和 [精度阶段](WORKFLOW.md#24-分阶段计算图精度与证据范围)交付 |

默认目标是在共同输入与约定策略下比较原生执行栈端到端结果，而非强求内部逐算子一致。
各层的实现与验证范围见 [README](../README.md)；详细检查、采集、任务和精度规则统一由 WORKFLOW 定义。
客户端入口只承担加载、参数交接与展示；核心和执行器独立于模型 API 及客户端专属工具。
按实际客户端与版本验收入口，以具体任务驱动三层之间的适配。

## 2. 共享能力

| 能力 | 输入与观测 | 对齐要素 |
|---|---|---|
| 前向/评分 | 固定输入和模型状态；目标 logprob 或张量 | token、位置、mask、评分分布、dtype |
| 缓存/有状态执行 | 初态与固定历史；输出及状态转移 | 坐标、布局映射、生命周期、原生/注入范围 |
| 目标/反向 | 共同目标依赖；目标值与梯度 | reduction、归一化、累积、缩放、通信、裁剪阶段 |
| 优化器更新 | 参数和优化器初态；更新前后状态 | 公式、超参、step、主权重和状态映射 |
| 采样/rollout | 初态与采样条件或固定轨迹；轨迹与效果 | 实际随机量、终止规则、分叉位置、注入范围 |

推理以评分和状态为主；SFT 组合目标、反向与更新；RL 按具体目标加入轨迹依赖。
能力记录区分计划、可用和已执行，结论限定于实际覆盖。比较模式及分叉处理统一见工作流。

## 3. 测评、环境与执行目录

| 目录 | 归属 |
|---|---|
| `scripts/compare_scores.py`、`tests/`、`docs/` | 框架通用比较核心、测试与规范；不收纳具体案例的执行器、环境或运行记录 |
| `projects/<project>/scripts/`、`tests/` | 本项目多个 case 实际共用的执行器、适配逻辑及对应测试；没有共享内容时不建空目录 |
| `projects/<project>/environments/<硬件侧>/<框架与版本>/` | 项目独立环境声明、依赖与能力配置，可由多个 case 复用 |
| `projects/<project>/cases/<case>/` | 共同契约、双侧 manifest、README、WORK_LOG、专用 `scripts/`、`tests/` 与 `runs/` |
| `projects/<project>/cases/<case>/runs/<运行标识>/` | 单次执行的输入、观测、环境、状态与日志，或新的离线比较报告；原始运行产物不可改写 |

上述项目目录由使用者按任务创建；项目执行器、环境及运行产物不随通用工具分发。

项目环境按硬件侧及实际框架版本组织：

```text
projects/<project>/environments/
  <gpu|npu>/
    <框架与版本>/
      <项目环境声明及锁文件>
      setting.yaml
```

| 文件 | 内容 |
|---|---|
| 项目环境声明及锁文件 | 遵循项目已有环境管理约定，记录依赖、安装来源和版本；例如 pixi 项目的 `pixi.toml` / `pyproject.toml` 与 `pixi.lock` |
| `setting.yaml` | 框架实际构建身份、Python、硬件/驱动/运行时、数值开关和能力证据 |

环境身份记录包发行版本、运行时构建字符串、设备插件及驱动/运行时版本，设备能力由实际导入和最小执行确认。例如，`torch 2.9.0+cpu` 可由 `torch-npu` 注册昇腾后端，构建后缀与设备插件共同描述这套环境。
执行器按所需 API 和已验证的构建组合检查兼容性，运行记录保留完整版本字符串。依赖按当前执行路径选取，例如原生 Transformers/FSDP2 评分使用 Torch、设备插件和 Transformers。
两侧实际使用的共享实现库按相同发布版本准备；平台运行时与设备扩展按各自兼容关系配套。异版本比较按 [共享实现库版本](WORKFLOW.md#共享实现库版本)申请用户批准。
遵循项目已有的环境管理约定，优先复用匹配环境；容器等现成环境同样适用。
环境配置存放声明与证据，源码、环境实体和权重保持在各自位置；执行器提供调用能力。
每个 case 的双侧 manifest 分别用 `side_config.environment_config` 引用本项目所需环境配置，路径相对 manifest；`environment` 仍引用实际运行记录，二者不能互相替代。案例引用自身 `runs/` 产物，环境可复用于多个测评。
任一侧尚未接入时记录待准备。模型、源数据与环境实体保存在外部资源位置，环境配置和案例交接引用资源位置及准备记录。共享只读目录或固定快照可由多个 case 和双侧执行复用；运行记录保存实际加载绑定，检查方式见 [共享资源与来源复用](WORKFLOW.md#共享资源与来源复用)。
适用性证据绑定“库版本 × 环境 × 能力 × 契约版本”。

## 4. 输入与产物边界

共同契约管理双侧约定，每侧 manifest 管理实际观测及证据引用。交接格式、字段和路径规则由 [WORKFLOW §2.1](WORKFLOW.md#21-版本化单侧交接) 统一规定。

| 对象 | 必需信息 |
|---|---|
| 比较请求 | 场景、硬件、库及已有环境、用户问题和所需范围；支持任一侧先建立 baseline |
| 冻结契约 | 共同语义、输入状态、数值条件、映射、reference、指标/阈值和必需覆盖 |
| 能力与授权记录 | 计划/可用/已执行能力、允许操作、设备与预算、停止条件和范围变更 |
| 来源与输入状态清单 | 库/模型来源与版本、实际配置与环境、数据来源/选取规则、共用输入及 case/token/mask/位置、初态/随机量、分片/坐标 |
| 工作记录 | 任务摘要、关键步骤与证据、结束摘要；格式及篇幅见工作流 |
| 双侧观测 | 有身份与坐标的评分、目标、梯度、更新或必要张量；有效数量、原始产物位置及注入边界 |
| 诊断报告 | 执行情况、可比性、指标与状态、覆盖和阻塞、证据及原因假设、执行器/核心版本 |

共享实现库的共同目标版本或获批版本配对归案例比较条件，两侧实际版本及构建身份归各侧环境记录。设备、平台运行时、分片、数值开关、kernel/融合及内部例外归每侧配置；模型/输入身份、参数存储 dtype、量化、autocast 策略、独立评分语义和必需覆盖归共同契约，双侧约定策略一致。
执行器与比较器的证据、算法职责见 [WORKFLOW §2.2](WORKFLOW.md#22-最小比较器)。
观测按约定范围保留可复核配对与计算的明细；工作记录和报告引用原始产物。
操作顺序、授权、输入对应关系、映射、采样范围、自检、公式与判定由 [WORKFLOW](WORKFLOW.md) 统一规定。

## 5. 离线核心依赖

`scripts/compare_scores.py` 仅依赖 Python 标准库，读取共同契约和双侧 manifest 引用的已有产物，与 Torch 和模型执行器隔离，不触发模型运行。
当前为 schema v2 / core 2.0.0，无 v1 兼容。报告区分固定算法定义、契约声明有效性与实际执行位置；未计算 P99 不记为已执行。inventory 派生和通用策略 DSL 不在实现范围。
接口、支持范围及确定性校验规则见 [WORKFLOW §2.2](WORKFLOW.md#22-最小比较器)。
