# 工作流与校验规则

[返回 README](../README.md) · [架构设计](ARCHITECTURE.md)

## 1. 从用户输入到报告

1. **发现信息与补齐决策**：复用用户输入、已有配置和产物，在允许范围内查明可确定的事实；对当前阶段需用户决定的缺项（如目标、模型/数据、设备授权与预算），给出有依据的推荐、主要影响及少量选项，支持自定义并集中确认。确认后冻结本阶段条件，后续决策按需提出，已知信息和已批准事项不重复询问。
2. **约定条件与最小采集项**：依据比较问题确定共同语义、必需覆盖、指标、阈值或未设阈值状态；在契约与每侧交接约定中明确需要保存的输入及坐标、端到端观测、实际执行条件和完成状态，以及各项证据的采集方式。不默认采集逐层激活、内部状态或算子输出。
3. **准备环境**：复用匹配环境或按架构中的环境规则准备，核验实际依赖、构建和数值配置；版本变化时重新核查接口、语义和能力证据。关键条件明确并冻结后执行比较。
4. **最小跑通并验收产物**：用最小 case 运行原生路径，同时验证输入、计算与采集链路；检查保存的产物能否按约定交接并进入比较，发现必要证据缺项先解决，再扩大执行范围。已有匹配产物可复用，无须重复运行。
5. **端到端比较**：在约定范围内先核验身份、状态、配对、有限性与覆盖，再计算指标。条件不一致或必要证据缺失先解决可比性问题，不直接进入模型内部定位；无阈值时只报告差异，不判通过。
6. **异常定位**：仅在预定阈值触发、非有限值或其他异常证据出现时，从异常 case、位置或阶段出发，按需增加内部观测，逐步缩小到模块和算子复现。非零差异本身不触发全面 dump；修复或优化后回归原端到端 case。
7. **报告与停止**：分别记录执行情况、可比性、数值判定及所有阻塞，保留产物位置与最小验证建议；无进一步异常定位依据时结束，达到停止条件或预算边界即停止相关执行。

### 授权、故障与预算

- **原授权内自主处理**：依赖安装、当前进程包源、路径、版本对应 API、序列化及不改变计算语义的工程 bug，无须重复请示；新适配/代码修改仍受已批准文件范围约束，每批最多 3 文件。修 bug 先用临时测试复现，修复后回归并删除该临时测试，不删除已有测试。
- **变更须确认**：不自动改指定版本、模型、输入、dtype、评分语义或约定后端；不扩设备/预算、不改全局权限、不替用户接受条款，不在原授权外新建外部连接或传输数据。安装和当前进程包源调整也不能绕过这些边界。
- **先停再修**：当前执行失败即停并保留日志/产物；工程故障可依据证据修正后有限重试。同一阻塞修正一次仍失败则报告，不重复试探；数据或语义错误不得靠跳过样本、换精度掩盖。
- **累计预算**：新任务明确设备范围、产物位置、规模与累计设备时长；加载、失败尝试和诊断均计入，安装/下载预算单列。启动或重试前核对剩余额度，触及上限即停；单次上限不是无限重试授权，不追溯改写历史授权或运行事实。
- **优化另行批准**：提交证据、方案、允许修改范围和验收口径，经用户批准后实施并回归原端到端 case；性能声称另需匹配的性能对照。

冒烟只验证路径与采集；指定范围比较只回答该范围内的数值问题；异常定位须有异常证据，用户指定调查也先明确待验证现象，不自动扩成全量 dump。
关键共同语义核验实际生效值，必要条件缺证据则报告阻塞；其他未知项列为覆盖限制，不强制检查全部内部张量。
仅在阶段完成、实质阻塞或需决策时汇报；复用后台完成通知及已有验收证据，不轮询或重复全量预检。

记录数据来源、选取规则及双方共用的实际输入，保留必要的路径、读取/解码和内容检查，复用已有验收证据。
**不需要输入指纹／哈希校验，不将其作为常规步骤或执行前置条件。** token、目标位置和 mask 的对应关系仍须核对；仅在传输损坏或文件混用疑点出现时专项检查文件一致性。
张量合约及前反向冒烟使用已授权空闲设备，无须重复全量 CPU 预检；按需采集，保持最小运行规模。
GPU 或 NPU 均可先建立单侧 baseline，交付输入、配置与观测，另一侧据此构建环境并执行；对照条件不匹配时先报告并确认处理方式。
执行先后与 reference 方向分开，先运行的一侧不自动成为 reference；单侧完成与双侧诊断分别报告。
两侧可独立执行并离线交付。复用产物须匹配冻结条件、来源与状态，保留其原有覆盖及阈值限制。
执行器保持库的原生路径，记录实际配置及注入范围；受控诊断变体单独确认、标注。
单算子复现固定输入、状态、dtype、shape、布局/mask、随机条件和语义，记录后端并比较必要输出与反向。
发现异常后，说明怀疑的问题及验证方法，再增加必要观测；没有进一步调查的依据就结束并报告。
局部差异构成定位证据，根因声称还需因果验证；算子结论与端到端结论各自限定范围。

### 1.1 有界原子任务

每次只派发当前阶段的任务，输入必须给出相关文件/字段、冻结条件、允许动作及文件范围、设备/累计预算和停止条件；上一阶段交付作为下一阶段输入，任务说明沿用案例工作记录，可复用同一代理。

| 任务 | 输入 | 动作 | 交付 | 停止/转交条件 |
|---|---|---|---|---|
| 产物盘点 | 请求、已知契约/manifest 与限定目录 | 列出引用、版本、运行范围及已有验收 | 可复用产物位置、缺失引用及范围 | 目录/身份不明即集中澄清，不全库搜索 |
| 按规则核验 | 盘点、冻结契约、§2.3 检查表 | 优先运行已有确定性检查；核对运行记录与证据范围 | 逐项证据位置、检查结果及核心报告 | 必要项不足转缺口调查，不由 agent 判数值或豁免 |
| 缺口调查 | 失败字段、已知日志/清单与查找边界 | 只查相关现存记录，区分事实、表达、冲突和责任问题 | 缺口分类、候选证据、最小处理建议 | 边界内无证据即停；未决语义交用户，表达能力不足交工具设计 |
| 采集准备与实施 | 已确认语义、真实缺项或新运行需求、授权与采集约定 | 按 §1.2 准备并最小运行，先验收再扩大 | 输入/观测/环境/状态、有效引用与验收结果 | 契约未决、授权不足不启动；技术失败保留产物，按故障规则处理 |
| 端到端比较 | 已验收双侧产物、冻结契约、新报告位置 | 用确定性核心核验并计算，不人工补值 | 报告、覆盖、全部阻塞 | 必要证据阻塞转调查；无异常依据则结束 |
| 异常定位 | 端到端异常证据、待验证假设、限定范围与授权 | 增加最小内部观测，局部复现后回归 | 定位证据、假设支持范围、回归结果 | 无新依据或触及预算即停；变更语义/范围重新批准 |

盘点任务先交付并验收，再以其结果启动核验任务，不在盘点中提前执行核验。只读子任务返回结构化交付：任务范围、产物/字段位置、实际动作及结果、缺口/阻塞、下一步；不要求写文件或日志。主会话汇总各阶段交付，统一维护案例工作记录；有写权限的任务仅保存获准产物并返回位置，不擅自扩大写入范围。

契约未决、授权不足和技术失败分别记录。缺口分类用于任务转交；报告状态按 §6 判定。

### 1.2 采集先行与交付验收

执行前按 §2.3 逐项约定谁采集、保存在哪个已有产物及字段、采用什么形式、如何验证和缺项如何停止；使用 `common`、`actual`、`evidence`、`environment`、`status` 等现有字段及案例工作记录。核验执行器对所需采集和输入回放的支持；必要语义无法由当前接口表达时，先报告阻塞并确认适配方案。

- **输入与坐标**：保存可回放的实际输入、位置、mask 与目标对应关系；声明来源和选取范围。
- **端到端观测**：保存可配对、可重算的明细；不以 summary 或逐层 dump 替代必要明细。
- **实际条件与完成状态**：执行器保留原生模型接口，负责采集运行事实、精度阶段证据及各预期 rank 的 environment/status；请求配置不能替代生效证据。
- **最小交付验收**：小规模执行同时验证可保存/读取、坐标完整、引用可解析、必需项满足当前核心的类型与证据规则；单侧只验交付，不宣称双侧通过。采集未验收不得扩大执行。
- **复用与补采**：先复用冻结条件匹配的产物；仅凭 null 不提出重跑，先走缺口调查。真实缺项才提出最小补采方案；优先回放保存输入，执行器未支持回放时先确认适配，新产物写入新 run，保留原始记录。

### 简短工作记录

每次诊断在 `projects/<project>/cases/<case>/WORK_LOG.md` 保留记录，不另设框架流水文档；工具测试与案例实际执行证据分开记录，不互相替代。新记录要求：任务摘要最多 10 行，结束摘要最多 10 行；按关键动作追加步骤，每步最多 6 行、200 字。
任务摘要记录场景、环境、模型/数据与授权范围；结束摘要记录完成项、未解决项和报告/产物位置。
步骤统一采用以下格式，记录环境准备、跑通、采集、比较和定位，不逐条记录工具调用；完整命令与长日志通过路径引用。

```text
步骤：做什么
依据：为什么做
执行：关键配置、命令或脚本位置
结果：成功／失败／阻塞及关键发现
证据：日志或产物路径
下一步：继续动作，或待用户确认的问题
```

## 2. 冻结比较契约

默认比较共同输入、约定数值策略和评分语义下两套**原生执行栈的端到端结果**。框架、kernel、融合及内部精度实现差异是比较对象，不要求逐算子一致。双侧参数存储 dtype、量化和 autocast 策略一致；框架配置写法可不同。

| 内容 | 最低要求 |
|---|---|
| 问题与覆盖 | 操作、场景、比较模式、必需能力、观察点、完整或采样范围及选点规则 |
| 双侧身份 | 库/提交/补丁、框架/依赖、硬件/驱动/运行时、实际执行配置 |
| 模型与输入 | 官方仓库/revision、实际权重/tokenizer/config 身份、数据来源与选取规则、case 和共用实际输入 |
| 目标语义 | token/预测位置、标签、mask、目标函数、reduction、全局归一化及评分分布 |
| 数值条件 | 共同参数存储 dtype、量化、autocast 与独立评分精度；每侧记录数值开关、kernel/融合及已知内部例外，未知保持未知 |
| 状态与映射 | 参数/缓存/优化器/调度器/缩放器初态、顺序、实际随机量、分片/坐标映射及注入边界 |
| 判定条件 | reference 身份、指标计算与汇总规则、事前阈值、硬约束、必需覆盖和停止条件 |

关键条件未知时集中澄清；共同子范围可单列，结论随覆盖收窄。
布局差异通过可验证的转置、重排、分片重组或参数映射对齐，映射依据语义而非对结果拟合。
阈值绑定指标、reference、范围、聚合规则及模式，在目标比较执行前冻结；独立基线可研究噪声，当前差异不用来倒推通过条件。

### 2.1 版本化单侧交接

评分交接闭环为 **共同条件 → 单侧交接 → 对照侧执行 → 离线比较**。具体测评在 `projects/<project>/cases/<case>/` 维护共同契约、每侧 manifest、README、WORK_LOG 与专用 `scripts/`；双侧各自通过 `side_config.environment_config` 引用项目 `environments/` 内的配置（相对 manifest），实际运行证据仍由 `environment` 引用。未接入侧只记录待办，不虚构 manifest 或结果。输入、观测、环境、状态和日志存入该案例 `runs/<运行标识>/`，离线报告也写入案例的新 run 目录。历史运行产物不改写、不覆盖。

共同契约与每侧 manifest 均为 `schema_version: 2` 的 JSON。下表概括内容，完整字段/类型以[比较器模块 docstring](../scripts/compare_scores.py)为准；执行器交付的输入、观测与证据须符合比较器字段契约，schema 版本由契约与 manifest 承载。

| 对象 | 最小内容 |
|---|---|
| 共同契约 | 模型、权重、tokenizer、config 来源身份；共用输入引用；参数存储 dtype、量化及 autocast 约定；`eval`、`no_grad`、full-forward、`use_cache=False`；FP32 自然对数 logprob；正文目标 t 对应预测位置 t−1；GPU reference；token 加权 NLL、MAE、全有效集合 P99；必需覆盖；`thresholds: null` |
| 每侧 manifest | side；输入、逐 token 观测、summary、environment、status 的引用；实际共同条件及证据出处；预期 rank 与执行完成状态；未覆盖项；设备/框架版本/分片/原生 kernel 等侧配置 |

- 所有资源路径相对所属 JSON 文件解析；交接可调整资源位置，旧绝对路径不充当来源身份。无需复制权重、conda 环境或重新分词。
- 声明与核验证据分开：`actual`/`evidence` 只包含 `common` 中除 `target_shift`、`reduction`、`percentile` 外的字段，拒绝额外键；实际事实未知值为 null；`evidence` 引用实际运行记录，接受规则见 §2.2。身份使用非空 `{repository, revision}`，不能从旧路径或请求配置推断实际加载身份。
- 必要条件缺证据即阻塞，并记录缺口原因；适配或补录依据实际证据，遵守核心核验规则。内部 state dtype 和具体 SDPA kernel 列为覆盖限制，不额外强制为 full-forward 共同条件。
- 对照侧复用保存的原始 token、位置和 mask，返回同坐标逐 token logprob、实际环境和执行状态。平台原生 kernel 可不同，但共同语义不能变；连接、安装、执行和外传仍须取得对应授权。
- 交接保留原始运行记录与契约建立时间，区分既有观测与事前冻结条件。具体文件、接收任务及阻塞记录在使用者创建的案例文档中。

### 2.2 最小比较器

[比较器](../scripts/compare_scores.py)为纯标准库实现，不导入 Torch 或模型执行器，不触发模型执行。

- API：`compare(contract, reference, candidate)`，三个参数依次为共同契约、reference manifest、candidate manifest 的文件路径，返回结构化报告。
- CLI：`--contract --reference --candidate --output`；报告独占创建、拒绝覆盖。退出码 0 表示诊断可得，1 表示已写出阻塞报告，2 表示参数/输出错误；通用示例见本节末尾。
- 读取符合字段契约的输入、逐 token 观测及选样/边界证据；字段名、类型和接受规则以比较器模块 docstring 为准，不因执行器不同而豁免。不重新分词；根据保存的实际数组重新验证目标对应关系。
- 核对来源、实际共同语义及预期 rank 完成状态；按 `(source_row_1based, prompt_id, target_position)` 配对。核验 case 完整历史、input/position IDs、attention/score mask、目标 ID、shift、数组长度、唯一性和缺失/额外项；允许记录重排，不静默取交集。
- 逐 token 检查有限性与 logprob ≤ 0（零合法，正值不设 epsilon 豁免），重算计数与汇总，不信任 `finite: true`。使用 Python 双精度、固定排序、`math.fsum` 和 §5.2 的全有效集合线性插值 P99；仅对已有汇总的舍入误差使用 `rel_tol = abs_tol = 64 * sys.float_info.epsilon`，不是业务阈值。
- 报告核心/schema 版本、输入证据路径、执行情况、可比性、数值状态、覆盖、全部阻塞和指标。缺观测记未覆盖；语义/重复冲突、空集或非有限记不可比；解析/计算未完成记执行失败，多阻塞全部保留。
- schema v2 / core 2.0.0：不接受 v1 或旧 `compute_dtype` 键，不隐式转换。`actual/evidence` 的字段集合见 §2.1；多余字段错误给出具体位置。
- 运行事实采用逐字段 exact-pointer：`evidence` 中 JSON 路径与 pointer 所指值须严格等于 `actual`（包括类型与对象完整键集），不接受 contract/manifest 自证、null 或补造记录。这是字段一致性检查，不是真实性认证；请求配置、当前源码和自由文本不自动成为运行证据。
- `common.autocast` 为精确对象 `{"enabled": false, "target_dtype": null, "scope": "model_forward"}`。`enabled` 必须是 JSON bool；开启时 `target_dtype` 必须为 `float32`、`float16` 或 `bfloat16`，关闭时必须为 null；`scope` 固定 `model_forward`，不接受其他键。每侧 `actual.autocast` 必须与共同对象一致，`evidence.autocast` 指向实际记录中的完整对象。枚举合法不代表框架支持，执行器须核实可执行性。
- 契约仍固定 `target_shift: -1`、`reduction: "target_token_weighted"`、`percentile: "global_linear_0.99"`，错误声明拒绝；三项不进入各侧 `actual/evidence`。shift 由真实数组关系验证，计数/NLL/全有效集合 P99 由核心计算；summary 数值仍重算核对，不索取旧 summary 的算法文本证明。
- 报告 `rules` 逐项记录固定 `definition`、契约 `declaration_valid` 和 `executed_at`。执行位置对应数组 shift 检查、各侧 NLL 重算或配对 P99 计算；空列表表示未执行，执行过检查不等于通过。错误声明不会成为执行规则；阻塞时仍可能有固定规则的单侧重算，但未计算 P99 不标为已计算。
- 尚未实现 inventory 派生或任意策略 DSL；现有接口无法接受的事实保留来源并转交适配，不以人工聚合或“已验证”字段替代核验。
- v2 只支持 `thresholds: null`，非 null 明确拒绝而非忽略，不输出通过/超阈值。cache/SFT/RL 未覆盖；核心不计算张量 relative L2，也不提供通用适配平台。
- `side_metrics` 保留可重算的单侧诊断，`metrics` 仅在完整可比时给出；未知条件不因同文件自比较而豁免，非法 logprob 同时阻塞受影响侧的 NLL 诊断。

[永久测试](../tests/test_compare_scores.py)覆盖已知指标、重排与坐标/语义冲突、缺失/重复/非有限/正 logprob、rank、汇总、错误输入、多阻塞及输出保护；实际测试结果与具体任务执行结果分别记录。自比较仅验证离线读取与计算，跨设备结论须有双侧实际观测及共同条件证据。

从工具根目录调用的通用示例（以下路径均为示意占位路径，不是随包文件或文档链接；执行前替换为实际契约、双侧 manifest 和不存在的新报告路径）：

### 2.3 预定义证据检查表

下表规定检查位置、形式、负责方及缺项出口；字段、类型和证据接受规则统一见 §2.2。引用路径相对所属 JSON，`evidence.<字段>` 的 `{path, pointer}` 相对 manifest 定位证据文件及其中的 JSON 值。执行器交付事实，核心确定性核验，agent 组织检查、追溯与转交。

| 检查项/范围 | 约定位置与形式 | 验证与负责方 | 缺项出口 |
|---|---|---|---|
| 实际加载身份 | `actual` 的 model/weights/tokenizer/config 及相应 `evidence`；运行记录中的 `{repository, revision}` | 执行器记录加载事实；核心按 §2.2 核验，agent 核对所引记录的角色 | 查加载记录；只有路径或请求配置不成立，事实缺失再提补采 |
| 输入、目标与覆盖 | 契约/manifest 的 `inputs`；保存的 token、position、mask、target 数组及选样/正文边界记录 | 核心重验数组关系、完整历史、shift、唯一性及双侧覆盖；无需重新分词 | 查原始输入与边界记录；冲突保留，不重选样本或静默取交集 |
| 运行模式与量化 | `actual.training/no_grad/forward/use_cache/quantization` 与逐字段 `evidence`；实际执行记录中的对应值 | 执行器记录生效模式；核心核对精确值。`eval`、无梯度产物或源码意图均不能替代 `no_grad` 运行证据 | 有界查日志/上下文记录；无记录保持未知，不能事后补造 true |
| 精度阶段 | `actual.weight_dtype/autocast/logprob_dtype` 与 `evidence`；`environment` 中相关阶段观测及已有参数 inventory | 核心分别核验存储、前向策略与评分精度；inventory 只支持其覆盖的存储事实 | 策略缺实际记录先调查；只有 inventory 等未支持表达时保留来源并转交适配 |
| 评分语义 | `actual.log_base/target_scope/distribution` 与 `evidence`；评分执行记录及保存数组 | 执行器交付实际评分路径，核心按 §2.2 核对字段并重验目标关系 | 查相关评分记录；意图与观测冲突先澄清，不切换评分定义 |
| shift 与 reduction | `common.target_shift/reduction`、输入/目标数组、`summary` 及逐 token `observations` | 核心拒绝非固定规则，重验 −1 关系并按 §5.2 重算计数/NLL、核对 summary；无逐侧算法证据要求 | 数组错位或汇总数值不符保留冲突；缺明细保留覆盖阻塞 |
| P99 算法 | `common.percentile`、双侧逐 token 观测及核心版本/规则报告 | 核心接受固定定义，完整可比时按 §5.2 计算全有效集合 P99 | 错误算法声明拒绝；必要证据阻塞时 P99 未执行，不向执行器索要算法证明 |
| 明细、有限性与完成 | `observations`、`summary`、逐 rank `environment/status`、`expected_ranks` 与 `execution` | 执行器保存明细和完成事实；核心验有限性、数量、汇总及所有预期 rank 的完成状态 | 缺 rank/观测记覆盖阻塞；已尝试但未完成保留失败与产物 |

**统一查找与出口**：约定位置 → 仅在已知相关产物中有界调查 → 分类 → 提最小方案。已有直接证据满足 v2 时复用并交核心核验；字段 null 但 inventory/数组中可能有事实时，先记录来源、覆盖和可验证关系，不能直接判定需要重跑。分类如下：

- **事实缺失**：限定记录中没有必要运行事实，报告最小补采项及所需授权。
- **表达不支持**：有候选事实，但 §2.2 的接口不能表达/接受；保留来源和阻塞，提出工具适配方案。
- **冲突**：声明、证据或产物互相矛盾，保留双方位置并调查，不择取有利记录。
- **责任定义待澄清**：运行事实与派生关系/算法职责未分清，先确认归属，再提出实现方案。

调查时区分直接运行记录、数组关系验证、清单派生和算法定义，按 §2.2 判断适用形式。达到查找边界仍缺必要证据时结束调查，按 §6 报告阻塞。

### 2.4 分阶段计算图精度与证据范围

精度约定按比较目标相关的阶段分别记录覆盖对象/路径和证据位置，区分**配置意图、实现约定、运行观测、未知**，结论限定于证据覆盖的阶段。

| 阶段 | 需要区分的语义与证据边界 |
|---|---|
| 参数/输入存储 | 参数、buffer、输入各自的存储 dtype 与覆盖；参数 inventory 仅证明所列对象，不证明算子计算精度或未列对象 |
| autocast 与前向 | autocast 启用状态、目标 dtype、作用范围；相关阶段输出/累积精度及内部例外分别说明，策略或输出 dtype 不等于所有内部运算 dtype |
| 评分路径 | logits 来源、转换发生位置、log-softmax/logprob 路径及相关精度；参数 BF16 与 FP32 评分可以并存，须分别有证据 |
| 保存与离线计算 | 保存前转换、文件表示与比较器计算精度；最终 FP32 输出不证明内部累积全为 FP32，离线 Python 双精度不证明前向精度 |

端到端比较只要求目标相关的必要阶段及证据，不默认遍历整图、采集全量张量；未观测的内部细节列为未知/覆盖限制。若某项是本次问题的必要条件，不能用限制说明替代证据，须保留阻塞。full-forward 的非必需内部项见 §2.1。

`autocast` 只描述前向上下文，不覆盖独立的评分精度，也不能由参数 BF16 或评分 FP32 推断。参数精度、autocast 和评分精度的证据不构成内部计算/累积精度的全图证明。框架混合精度设置、数值开关、kernel/融合和已知例外记录在 environment 或侧配置中，可不同，不因此单独判不可比。若要求额外某项一致，须在执行前明确范围和验证方案；v2 不自动校验未实现的条件。

## 3. 推理 baseline

### 3.1 模型、样本与序列化

- 以 Hugging Face 官方模型权重、tokenizer 和 config 为锚，通过仓库/revision、配置及加载记录核对双侧实际加载身份。
- 单轮样本取数据集首个 user 及随后 assistant；有 system 则保留。使用官方格式；Base 模型无官方 chat template 时明确共同序列化，不擅套 Instruct 模板。
- 在运行前按两侧共同长度预算选取完整样本，保持不截断；记录原始/纳入/排除数量、排除原因和覆盖范围。
- 沿用数据来源与现有划分，不做数据集重划分。独立 train/val/test 不是数值一致性的前提，但影响泛化效果声称。
- 官方格式要求的 BOS、角色、分隔符及终止特殊 token 保留在序列化中；主指标只评分 assistant 正文，排除这些特殊 token、system/user 和 padding。
- 可靠确定正文 token 边界，核验 tokenizer 后的目标位置与 mask；边界无法可靠确定时，先报告可比性阻塞。`target_scope` 保留实际记录与证据要求，数组或正文 span 不独立证明特殊 token 已排除；核心不加载 tokenizer 或新增 special-ID 体系。

### 3.2 运行和评分

双方保持相同权重、token 序列、输入位置、attention/score mask、参数存储 dtype、autocast 策略、量化状态和独立评分定义，并核验实际生效值而非只看配置。
允许 CUDA/CANN 及平台原生 kernel、融合路径不同，记录执行栈；不为降低误差自动切 eager 或改变精度。
使用 `eval` 与无 autograd 的前向。teacher forcing 输入固定完整序列，按真实目标 token 评分，既不采样也不做 greedy 选择。
默认先比较 full-forward；logits 的预测位置与下一目标 token 对齐，使用共同的原始模型评分分布。
可选 greedy 生成仅用于分叉诊断，不作为主精度指标；自由生成分叉后按轨迹问题处理。
设备和依赖可能同时变化，因此报告执行栈差异；纯硬件或特定算子归因需要额外定位证据。

### 3.3 cache 的独立覆盖

cache 路径另列覆盖项，固定共同 token 历史、位置、初态及可信布局映射。
各自 cache 沿固定 token 链演化时，测得的是累积差异；共同 cache 注入下的一步才是同状态的孤立 decode 对照。
未暴露的 cache 观测记为未覆盖，已有评分项独立报告。

## 4. SFT、RL 与状态分叉

SFT/RL 复用评分、目标、反向和更新能力，标量目标保留数值与定义；作为验收项时可复用标量 relative L2。
同状态比较冻结参数及可信映射、优化器、step、调度器、loss scaling，核对 batch/微步顺序、累积、全局 token 归一化、通信和裁剪阶段。
完整训练状态以实际恢复证据为准，单独恢复权重或小张量回读只覆盖对应范围。
记录 train/eval、dropout、采样和随机算子；相同 seed 不保证跨库/设备实际随机量一致。
必要时提供共同随机量或固定样本；无法控制时明示严格对照限制，保留原生行为与受控变体的区别。

RL 先明确具体目标及依赖，不默认 PPO。固定 rollout 的 prompt/response、有效 token、终止与截断规则；按目标冻结 old/reference logprob、reward、advantage、return 及来源。
核对 clipping、KL 定义、权重和 token/序列归一化；共同量注入只覆盖下游，产生这些量的上游过程单列覆盖。

| 比较模式 | 结论边界 |
|---|---|
| 同状态数值校验 | 比较点具有共同输入、初态、目标依赖和实际随机条件证据 |
| 自由轨迹/训练效果 | 允许状态或历史演化，另行冻结任务、数据划分、生成设置及效果指标 |
| 同设备版本回归 | 冻结设备及其他条件，明确 reference 版本和变化范围 |

首次更新后参数或优化器状态分叉，后续结果属于轨迹差异；检查后续同状态步骤须重新提供共同状态。
生成/rollout 分叉后，同序号的不同 token 或历史各自保留，停止逐位置同输入解释。
数值指标描述一致性，任务效果需独立评价；评分能力仅覆盖评分，不替代反向或更新。

## 5. 配对与最小指标

### 5.1 有效集合

令 V 为契约内全部有效目标 token 的配对集合，N = |V|；逐对核对 case 身份、目标位置、目标 token、历史和 mask。
双侧观测要求无重复、无缺项，mask 和坐标一致；按约定排除 padding/ignore label 等位置，不静默取交集或丢弃未配对项。
N = 0 时评分指标未定义，记为不可比。缺观测保留未覆盖范围，语义/状态/映射冲突记为不可比。
有效浮点值及指标结果须有限；有效范围内 NaN/∞ 记为不可比，保留坐标、数量和原值。约定的无效位置及 attention mask 的 −∞ 哨兵按契约排除。

### 5.2 token 加权 NLL 与 logprob 差异

令 ℓᵈᵢ 为设备 d 在配对 i 上对共同目标 token 的自然对数概率，d ∈ {GPU, NPU}；默认 GPU 为 reference。

- NLL_d = −Σ_{i∈V} ℓᵈᵢ / N；ΔNLL = NLL_NPU − NLL_GPU，单位 **nat/token**。
- 跨 case、batch、rank 先累加负 logprob 总和，再除以全局有效 token 数，即 token 加权而非逐例等权。
- ΔNLL 的符号表示平均 NLL 方向；局部差异可能抵消，须同时报告以下绝对差指标。验收事前指定容许区间或绝对值规则，负值本身不代表通过。
- 在同一 V 上，e_i = |ℓᴺᴾᵁᵢ − ℓᴳᴾᵁᵢ|；MAE = Σe_i / N，单位 nat。
- P99 使用整个 V 的 e 升序序列 e_(0), …, e_(N−1)：h = 0.99(N−1)，j = floor(h)，k = ceil(h)，P99 = e_(j) + (h−j)(e_(k)−e_(j))。
- N = 1 时 P99 = e_(0)。报告 N、插值规则与计算实现版本；样本分位数只代表本次有效集合，PPL 无须另作独立验收指标。

### 5.3 张量、梯度与实际更新 relative L2

默认 r 为 GPU reference，c 为 NPU candidate，在共同坐标上计算 **relative L2 = ||c−r||₂ / ||r||₂**。
记录张量/参数身份、flatten/拼接范围、计算 dtype、分子和分母范数；同设备回归明确 reference 版本。

| 条件 | 结果 |
|---|---|
| ‖r‖₂ > 0 | 使用上述公式；近零分母同时展示范数 |
| ‖r‖₂ = 0 且 ‖c−r‖₂ = 0 | 0 |
| ‖r‖₂ = 0 且 ‖c−r‖₂ > 0 | 未定义、不可比；报告原始误差范数 |

分母不加 epsilon。空坐标集合同样不可比，非有限值沿用 §5.1。
梯度采集须处于相同缩放、累积、通信和裁剪阶段。
实际更新分别计算 u_GPU = θ_GPU_after − θ_GPU_before、u_NPU = θ_NPU_after − θ_NPU_before，再以 r = u_GPU、c = u_NPU 比较；参数接近不替代更新比较。
分片/参数采样保留双侧共同坐标、数量及选点规则，结论仅覆盖采样集合。

## 6. 判定、覆盖与自检

| 逐项状态 | 判定规则 |
|---|---|
| 通过 | 执行证据完整、可比、指标有限且定义成立、满足冻结阈值、该项必需覆盖完整 |
| 超阈值 | 可比且定义成立的数值违反冻结阈值规则 |
| 不可比 | 语义/状态/映射冲突，或指标因空集合、非有限值、零 reference 非零误差而未定义 |
| 未覆盖 | 能力缺失、未执行、必要观测缺失或只有部分范围 |
| 未设阈值 | 可比且能报告数值，但无匹配的事前阈值；仅作诊断 |
| 执行失败 | 已尝试运行、采集或计算但未完成，保留错误阶段与已有产物 |

执行成功、可比性、数值判定分别记录，并保留全部阻塞原因；例如非有限且无阈值时主状态为不可比，同时记录缺阈值。
全部必需项均通过且必需范围完整，才可整体通过；通过子项与未覆盖子项并列展示。
无阈值可诊断，不判通过或超阈值；可比且有限的数值也不自动构成业务容忍度。

最小自检覆盖身份与来源、target shift/mask、覆盖计数和有限性；用同产物自比较验证零差异，再用小型已知差异核对公式、方向和状态。
自比较的零 reference、空集合及非有限值仍遵循定义域规则。已有自检证据可复用，输入或比较实现变化时针对受影响部分检查。

| 设计验收用例 | 必需检查 |
|---|---|
| 推理固定历史 | full-forward 的 ΔNLL/MAE/P99；cache 累积与共同 cache 孤立对照分别覆盖 |
| SFT 同状态一步 | 共同参数/优化器初态、目标和梯度阶段、after−before 更新、坐标覆盖 |
| RL 固定轨迹 | 具体目标依赖及归一化、原生/注入范围、评分/反向/更新各项覆盖 |
